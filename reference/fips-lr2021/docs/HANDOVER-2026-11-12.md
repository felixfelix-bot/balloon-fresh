# FIPS over LR2021 — handover, 2026-11-12

This is a practical handover for someone building or debugging a similar
LR2021/FLRC FIPS link in Archipelago. It separates **verified working results**
from the **unfinished 2.4 GHz throughput experiment**, so no partial result is
mistaken for a production baseline.

## TL;DR

- **The 868 MHz FIPS data plane works** on the bench: authenticated XK sessions,
  bidirectional IPv6 at 0/50 loss, HTTP at 128 KiB and 1 MiB, and SSH over the
  FIPS IPv6 address.
- The working radio setting is EU-868, FLRC-650, 128-byte air packets, 14 dBm.
  It is slow but demonstrably reliable.
- The 511-byte / EU-2.4 GHz experiment now delivers **20/20 unique packets in
  both directions** after fixing three concrete defects, but the strict
  100-packet zero-error gate still fails.
- Therefore **no 2.4 GHz FIPS, IPv6, HTTP or maximum-throughput claim exists
  yet**. `2.6 Mbps` is a raw FLRC air setting, not achieved application goodput.
- The default firmware source keeps CR 3/4. The **CR-none** speed experiment is
  opt-in with `-DLR2021_FLRC_CR_NONE=ON`.

## Verified baseline: EU-868 FIPS over LR2021

Measured on 2026-11-10 with host commit
[`c03rad0r/fips@8155e5ff`](https://github.com/c03rad0r/fips/tree/8155e5ffd4baada469ada15eeaa0a3d5bac83c6f),
and ESP32 bridge versions S3 `0.4.22` / NiceRF C3 `0.5.12`.

| Item | Verified |
|---|---|
| Air profile | EU-868, 868.1 MHz, FLRC-650, 14 dBm, sync `2dd4d4b2` |
| Air packet | 128 bytes (104 application bytes after link header/CRC) |
| FIPS authentication | Both peers authenticated; initiator + responder XK established |
| IPv6 | 50/50 replies in each direction, **0% loss** |
| Rekey | Real link/FSP rekey occurred; subsequent 50/50 gate also passed |
| HTTP 128 KiB | 3/3 exact-length HTTP 200; 147.019 / 167.250 / 138.060 s; mean **0.0070 Mb/s** |
| HTTP 1 MiB | 3/3 exact-length HTTP 200; 1275.047 / 1272.223 / 1313.169 s; mean **0.0065 Mb/s** |
| SSH over FIPS | `RADIO_SSH_OK`, public-key auth, exit 0 |
| Host tests | 25/25 FIPS LR2021, 4/4 native transport, 39/39 tracker driver at baseline |

The complete log names, metrics and raw byte counts are in
[`RESULTS.md`](RESULTS.md) and [`PING-RELIABILITY-PLAN.md`](PING-RELIABILITY-PLAN.md).

### Why the baseline was slow

1 MiB at 104 application bytes/packet requires about 10,082 radio fragments.
The measured 20 ms inter-fragment pacing alone costs about 202 s; CSMA guards,
ACK turnaround, retry recovery and TCP/FIPS overhead account for the remainder.
It was deliberately optimized for delivery correctness, not throughput.

The important host fixes that made this work are in
[`crates/fips-lr2021/src/link.rs`](https://github.com/c03rad0r/fips/blob/8155e5ffd4baada469ada15eeaa0a3d5bac83c6f/crates/fips-lr2021/src/link.rs)
and
[`src/transport/lr2021/mod.rs`](https://github.com/c03rad0r/fips/blob/8155e5ffd4baada469ada15eeaa0a3d5bac83c6f/src/transport/lr2021/mod.rs):

- batch-tail NACK instead of per-fragment ACK/retransmit storms;
- ACKs validated by peer ID and epoch;
- bounded asynchronous one-frame scheduling so repairs are not queued behind
  a whole TCP burst;
- optional fragment pacing (`packet_gap_ms`).

The reproduction scripts are:

- [`tests/hardware/ping-gate.sh`](../tests/hardware/ping-gate.sh) — strict
  bidirectional 50/50 gate; rejects any loss.
- [`tests/hardware/http-speed.sh`](../tests/hardware/http-speed.sh) — radio-only
  HTTP meter; refuses to run without 0% ping loss.
- [`tests/hardware/ssh-smoke.sh`](../tests/hardware/ssh-smoke.sh) — isolated,
  temporary-key SSH-over-FIPS test.
- [`tests/hardware/per.sh`](../tests/hardware/per.sh) — reciprocal unique
  payload/PER harness.

## EU-2.4 GHz / 511-byte experiment: what was learned

### Verified intermediate results

- The 128-byte 2.4 GHz control passed **20/20 in both directions**, proving the
  HF carrier path itself works.
- After all three fixes below, 511-byte CR 3/4 smoke tests passed **20/20 in
  both directions with zero link errors**.
- Strict 100-packet CR 3/4 runs delivered **100/100 unique payloads in each
  direction**, but recorded **1 and 6** host link CRC/framing errors.
- Strict 100-packet CR-none runs delivered **100/100 with 12 errors** one way and
  **99/100 with 13 errors** the other. One later startup failed to deliver.
- This is not enough to declare a stable 2.4 GHz link. No FIPS sessions, IPv6
  gate, HTTP test, SSH test or goodput number was attempted at 2.4 GHz.

### Three concrete faults found and fixed

1. **255-byte receive limit.** The ESP bridge and C++ driver had 255-byte RX/USB
   buffers, and the FLRC payload-length config narrowed 511 to 255. They now use
   bounded 511-byte buffers and a 16-bit FLRC length.
   Relevant source:
   [`main.cpp`](../firmware/esp32-bridge/main/main.cpp),
   [`lr2021_spi.h`](../../../tracker/firmware/components/lr2021_transport/include/lr2021_spi.h),
   [`lr2021_spi.cpp`](../../../tracker/firmware/components/lr2021_transport/src/lr2021_spi.cpp).

2. **Malformed extended-FIFO register writes.** The bridge sent a 4-byte address
   for `WriteRegMem32`; the LR2021 takes a **3-byte address followed by 4 data
   bytes**. The correction is covered by
   `test_extended_fifo_commands_match_datasheet` in
   [`test_lr2021.cpp`](../../../tracker/firmware/components/lr2021_transport/test/test_lr2021.cpp).
   Before this, a 511-byte frame arrived with `bad magic`; afterwards the frame
   began with the expected `F1 50`.

3. **Long SPI FIFO read corruption.** Reading the full 511-byte RX FIFO in one
   SPI transaction returned corrupt payload from around byte 151 onward. Reading
   in **128-byte chunks** produced correct FIPS frames and the 20/20 smoke
   passes. The chunked read is in `EspIdfLr2021Radio::read_packet` in
   [`lr2021_spi.cpp`](../../../tracker/firmware/components/lr2021_transport/src/lr2021_spi.cpp).

An independent cross-family review accelerated diagnosis. Its key finding—the
4-byte address in `WriteRegMem32`—was verified against the Semtech driver’s
three-byte encoding and the datasheet’s 9-byte command format.

### Why the strict gate still fails

The remaining failures are real link-layer CRC/framing errors, not stale header
bytes or incorrect packet lengths. Likely contributors are the 2.4 GHz link
margin with this antenna/power arrangement, uncoded/3-4 coded FLRC sensitivity,
and CSMA/retry contention. CR-none increased errors; CR 3/4 was better. No
acceptable result can be claimed until a strict run has zero unexplained errors.

## Reproduce the verified 868 MHz baseline

Prerequisites: two E80/ESP32 bridges, EU regulatory environment, a FIPS build
from the pinned fork, and the test identities/configs described in the onboarding
guide. Never use `us915`/`us2400` on this EU bench.

```bash
# 1. Host and link tests
make -C tracker/firmware/components/lr2021_transport/test test
(cd "$FIPS_DIR" && cargo test -p fips-lr2021)

# 2. Strict bidirectional IPv6 gate
NETNS_A=fips-lr-a NETNS_B=fips-lr-b \
IP_A=<A_FIPS_IPV6> IP_B=<B_FIPS_IPV6> \
COUNT=50 INTERVAL=1 ./tests/hardware/ping-gate.sh

# 3. Serve files on A's FIPS address, measure from B
NETNS=fips-lr-b PING_IP=<A_FIPS_IPV6> \
URL='http://[<A_FIPS_IPV6>]:18080/fips-http-128k.bin' RUNS=3 \
./tests/hardware/http-speed.sh

# 4. SSH smoke test
IP_A=<A_FIPS_IPV6> NETNS_A=fips-lr-a NETNS_B=fips-lr-b \
./tests/hardware/ssh-smoke.sh
```

The expected radio configuration is EU-868, FLRC-650, 14 dBm, 128-byte payload,
sync `2dd4d4b2`, `packet_gap_ms: 20`, `ack_timeout_ms: 300`,
`max_retries: 15`, minimal link/session MMP. The benchmark used long rekey only
as an isolation setting; production should retain normal rekey policy.

## Safety and operational notes

- Never exceed the hardware/regulatory requirements for the EU 2.4 GHz band.
- Use `/dev/serial/by-id/...`, not transient `/dev/ttyACM*` numbers.
- FIPS serial users must be stopped before probing/flashing; use the board-lock
  wrapper. This bench required a custom `fips-e80-pair` resource for the S3
  `34:85` and C3 `B0:A6` pair.
- Do not copy or commit private FIPS/SSH keys. Raw evidence must be non-secret.
- Distinguish radio-only HTTP measurements from public WAN/MCP measurements. A
  CDN result is not evidence that traffic used LR2021 unless the measuring
  process is confined to the FIPS namespace or runs on the far node reached over
  radio.

## 4. Verdicts

### 4a. Applying the spec's rules to the mandated phases → INCONCLUSIVE

| direction | baseline_max | during_max | Δ | samples above +10 | spec verdict |
|-----------|--------------|------------|---|-------------------|--------------|
| A→B (phase 2, PA −18) | −55.0 | −58.0 | −3.0 dB | 0 | **INCONCLUSIVE** |
| B→A (phase 3, PA −18) | −64.0 | −94.0 | −30.0 dB | 0 | **INCONCLUSIVE** |
| staircase PA −10 | −55.0 | −33.0 | +22.0 dB | 1 | INCONCLUSIVE |
| staircase PA 0 | −55.0 | −33.0 | +22.0 dB | 1 | INCONCLUSIVE |
| staircase PA +10 | −55.0 | −63.0 | −8.0 dB | 0 | INCONCLUSIVE |

Not DEAD either: every `during` sample is **not** within ±5 dB of
`baseline_max` (worst deviation 35–45 dB), and the baseline maxima themselves
(−55 / −64 dBm, measured with **no transmitter running at all**) exceed anything
seen while transmitting. Reported as INCONCLUSIVE, not rounded up or down.

### 4b. Why the mandated cadence cannot decide this (method finding)

`RSSI?` runs one CAD (`SX128x::scanChannel()`, `CAD_ON_8_SYMB` = 8 symbols ≈
2.52 ms at SF8/BW812.5), blocks on DIO1, reads the `RssiInst` register once, and
drops back to standby. The packet burst is ~12.6 ms of air time. At the mandated
cadence (1 TXPROBE/s, 1 `RSSI?`/0.625 s) the expected number of CAD/burst
overlaps in a 25 s phase is:

```
25 s × 1.0/s × 1.6/s × (2.52 ms + 12.6 ms) / 1000 = 0.6
```

i.e. **the spec'd phase can essentially never catch the burst** — a single
instantaneous sample would have to land inside a 12.6 ms window. So
INCONCLUSIVE here is a property of the sampling method, not evidence about the
RF chain. (Measured, this is exactly what happened: 0 detections.)

### 4c. High-rate sensitivity phase (clearly-labelled non-spec extension) → LIVE both ways

Same commands, same PA (−18 dBm), just sampled as fast as the boards answer:
`TXPROBE` back-to-back (2.5/s) and `RSSI?` back-to-back (**~206/s**).

| direction | samples | tx probes | expected overlaps | **detections** | Δ vs baseline_max | peak inst |
|-----------|---------|-----------|-------------------|----------------|-------------------|-----------|
| A→B | 6185 | 75 | 233.8 | **249** | **+31.0 dB** | −24.0 dBm |
| B→A | 6251 | 75 | 236.3 | **252** | **+38.0 dB** | −26.0 dBm |

* Expected-vs-observed agrees (249 vs 234, 252 vs 236): the detection model is
  sound, so the *zero* detections at the mandated cadence is a sensitivity miss.
* Delta vs the median noise floor (−98.0 dBm): **+74 dB / +72 dB**.
* 266 / 277 samples above `baseline_max + 10 dB` (spec needs ≥ 3).
* Only detected at **PA −18 dBm**, the minimum — no power escalation needed.

**Verdict: A→B LIVE. B→A LIVE.**

## 5. Energy present but packet not decoded — which did we see?

We saw **preamble energy present, full packet not decoded**:

* The CAD fires: 249 / 252 samples returned state **−702**
  (`RADIOLIB_LORA_DETECTED`) — a real LoRa preamble detection.
* The packet-RSSI field stayed `0.0` in **every** sample of every phase, so no
  complete packet was ever demodulated.
* This is expected and is **not** evidence about the link: `RSSI?` only performs
  a 2.5 ms CAD and then leaves the radio in standby, so the receiver is never in
  continuous RX long enough to receive a 12-byte packet. Full-packet decode was
  therefore **not exercised** by this test.

## 6. Firmware bug found (reported, not fixed — firmware was not modified)

`probe_rssi()` in `firmware/esp32-e28-range/src/e28_range_console.cpp` labels the
CAD result with:

```c
st == RADIOLIB_PREAMBLE_DETECTED ? "lora-preamble"   /* -14 */
: st == RADIOLIB_CHANNEL_FREE    ? "channel-free"    /* -15 */
: "scan-error";
```

but `SX128x::getChannelScanResult()` (RadioLib 7.7.1) returns
`RADIOLIB_LORA_DETECTED`, whose value is **−702**, not −14. A genuine preamble
detection is therefore printed as **"scan-error"**:

```
RSSI -0.0 dBm inst=-25.0 dBm state=-702 (scan-error)     <-- this IS a detection
```

Impact: anyone applying the spec's stated rule ("an inst rise *without* any
`lora-preamble` scan state means the packet is not being decoded") would read
249 real detections as scan errors and could wrongly conclude the RF chain is
dead. The label should compare against `RADIOLIB_LORA_DETECTED` (or treat any
non-−14/−15 code as detection). The tool compensates by decoding `state`, not
the printed label.

## 7. Final board state and safety

In-session final state (issued `PA -18`, confirmed by `STAT?`):

```
A: role=idle freq=2445 sf=8 bw=812.5 pa=-18 addr=0xE80E2801 last=none err=0
B: role=idle freq=2445 sf=8 bw=812.5 pa=-18 addr=0xE80E2801 last=none err=0
```

**Caveat (measured, not assumed):** these boards reboot when the host serial
port is opened, so nothing set over serial persists across a close/open cycle.
Re-opening the port later shows the firmware's boot defaults:

```
A: role=idle freq=2440 sf=7 bw=812.5 pa=3 addr=0xE80E2801 last=none err=0
B: role=idle freq=2440 sf=7 bw=812.5 pa=3 addr=0xE80E2801 last=none err=0
```

`pa=3` is the firmware's own `setup()` default. The safety-relevant invariants
hold in the persisted state: **role=idle and nothing transmitting**. PA −18
cannot be left persisted on this firmware; it is re-applied at the start of
every run.

Safety rules honoured: minimum power first; escalation only inside the defined
staircase (+10 dBm cap never exceeded); TXPROBE loop stopped at the end of every
phase; no `RANGE`/`RANGE-SLAVE` used; no firmware source modified; both ports
opened with `dtr=False, rts=False`.

## 8. Conclusion

The RF chain (PA, front-end switch, antenna path) is **LIVE in both directions
at the minimum power**, with +31 dB / +38 dB of margin over the phase-1 baseline
and 249 / 252 CAD preamble detections. **The ranging failure is therefore not an
RF-chain/PA/antenna problem.** What this test did *not* exercise is full-packet
demodulation (the `RSSI?` probe never holds the radio in continuous RX), so the
remaining suspects are the RX/IRQ-driven receive path and the ranging exchange
logic — not the transmit power chain.

## Q5 (HIGHEST VALUE) — Is a patch/PRAM load required? → **ELRS: yes, unconditionally. We: never.**

Verified live in the clone:

```
src/lib/LR2021Driver/LR2021.cpp:112   CHECK("LOAD_PATCH_RAM", LoadPatchRAM(SX12XX_Radio_1));
src/lib/LR2021Driver/LR2021.cpp:113   if (GPIO_PIN_NSS_2 != UNDEF_PIN) CHECK("LOAD_PATCH_RAM", LoadPatchRAM(SX12XX_Radio_2));
src/lib/LR2021Driver/LR2021Patch.cpp:9    #define LR20XX_PRAM_BASE_ADDRESS ( 0x801000 )
src/lib/LR2021Driver/LR2021Patch.cpp:42   uint16_t LR2021Driver::LoadPatchRAM(const SX12XX_Radio_Number_t radioNumber)
src/lib/LR2021Driver/LR2021PRAM.h:6       constexpr uint32_t PROGMEM pram_lr2021[560] = {
src/lib/LR2021Driver/LR2021_Regs.h:93     LR2021_PATCH_ENABLE_PRAM_OC = 0x012D,
```

**`Begin()` ordering (LR2021.cpp:98-152):** `hal.init()` → `hal.reset()` → `CheckVersion`
→ **`LoadPatchRAM`** → `SYSTEM_CLEAR_ERRORS_OC` → `SetMode(STDBY_RC)` → optional `SET_TCXO_MODE`
→ `SET_RX_TX_FALLBACK_MODE` → `SET_DEFAULT_RX_TX_TIMEOUT` → `SetDioAsRfSwitch`
→ `SYSTEM_SET_REGMODE` → `SYSTEM_CALIBRATE(0x7F, 10 ms)` → `CALIBRATE_FRONTEND(30 ms)`.

`LoadPatchRAM` implementation (LR2021Patch.cpp:42-71): writes the 560-word table as **32-bit
words** to `0x801000` in 12-word chunks (12 × 4 B = 48 B payload, chosen so command + payload fits
the 64-byte SPI buffer — comment at :44), then writes `LR2021_PATCH_ENABLE_PRAM_OC (0x012D)` with a
**single byte `0x00`** (:69-70, 10 ms).

**Our tree:** `grep -rniE 'pram|patch' firmware/rp2040/src/ tracker/firmware/components/lr2021_transport/src/`
→ **no hits.** We never upload a patch and never touch `0x012D`.

**Why this matters for us.** A patch RAM load is how the vendor delivers post-silicon PHY fixes
without a new chip revision; an unpatched LR2021 may exhibit exactly the class of defect we have
logged as unexplained — *short payloads (64 B / 128 B) at FLRC 260/650 kbps giving 200/200 CRC
errors while 255 B payloads at the same rates are clean*. That signature (payload-length-dependent,
bitrate-dependent, len-independent) is consistent with a PHY-side issue the patch would address.
**This is a hypothesis, not a proof** — see "What would settle it".

**`NOT REACHED` by the dead run:** it did not finish extracting whether the patch content is
mode-gated (FLRC-only vs LoRa too), nor a changelog for what the patch fixes. The 560-word table
is opaque words in `LR2021PRAM.h`; the vendor's own release note on it was not located.

### What would settle it (bench work, deliberately NOT done here)
1. Upload the ELRS PRAM table to our board via our own opcode path (we already write `0x01`/`0x02`
   opcode frames; the write needs the 32-bit memory-write opcode ELRS uses in `WriteRegMem32`).
2. Re-run our exact failing matrix: 64 B and 128 B at 260/650 kbps, plus the 255 B control.
3. Read back CRC/PER. A flip from 200/200 CRC to clean **confirms** the patch as the root cause.

## Q1 — Init ordering and delays

| Step | Ours (`esp_idf_lr2021_radio.cpp:init_sequence`) | ExpressLRS (`LR2021.cpp:98-152`) | Diff |
|---|---|---|---|
| reset | `hardware_reset()` | `hal.reset()` | same intent |
| version check | — | `CheckVersion` (gates init) | we do not verify chip identity at init |
| **patch** | **absent** | **`LoadPatchRAM` ×radio** | **SEE Q5** |
| clear errors | `0x01 0x11 00 00` (+1 ms) — **first** | `SYSTEM_CLEAR_ERRORS_OC` — **after** patch load | ordering differs |
| standby | `0x01 0x28 0x01` (`STDBY_XOSC`, +5 ms) | `SetMode(LR2021_MODE_STDBY_RC)` | **different mode** |
| TCXO | absent | conditional `SET_TCXO_MODE` from `HARDWARE_radio_tcxo` | we likely have no TCXO — confirm |
| fallback | `0x02 0x06 0x03` (Fs) | `SET_RX_TX_FALLBACK_MODE` = `LR2021_RADIO_FALLBACK_FS` | **same choice** ✓ |
| rx/tx timeout | absent | `FF FF FF 00 00 00` | we rely on defaults |
| DIO/RF switch | absent (RP2040 pio path?) | `SetDioAsRfSwitch()` | verify per platform |
| reg mode | absent | `0x02` DCDC / `0x00` LDO | power-efficiency delta only |
| **calibrate** | `0x01 0x22 0x5F` **+5 ms** | `SYSTEM_CALIBRATE(0x7F)` **+10 000 µs** | **arg AND delay differ** |
| **calib frontend** | `0x01 0x23 <2B> +6 zeros` **+5 ms** | `CALIBRATE_FRONTEND(4B)` **+30 000 µs** | **encoding AND delay differ** |
| packet type | `0x02 0x07 0x05` (FLRC) | set later, in the mode-config path | ordering differs |

**Delay finding is unambiguous and cheap to act on:** ELRS waits **10 ms** after the main
calibration and **30 ms** after the front-end calibration (both passed as explicit timeouts to
`WriteCommand`). We wait **5 ms** for each. Calibration not settling is a classic cause of flaky
sensitivity and of band-dependent failures. Raising our two delays costs nothing.

**Calibrate argument:** ELRS passes `0x7F`; we pass `0x5F`. Note our own source comments
"`0x5F` (NOT `0x6F`)", i.e. we already carry a note that this value matters. `0x7F` vs `0x5F`
differs in bit 5. Which bits are meaningful is **not established from the datasheet in this pass**
(`NOT REACHED`) — treat as REVIEW, and prefer the vendor-adjacent value (`0x7F`) unless the
datasheet says otherwise.

## Q2 — FLRC modulation params

| Field | Ours | ExpressLRS |
|---|---|---|
| FLRC mod params | `0x02 0x48 0x00 0x25` (bitrate 2600 = `0x00`, `0x25` = CR/BT byte) | set through `SetFlrcModulationParams` at mode-config time |
| sync word | `0x02 0x4C 0x01 <4B>` | `SetFlrcSyncWord` |
| packet params | `0x02 0x49 0x0C 0x4C 0x00 <len>` | `SetFlrcPacketParams` |
| CRC in packet params | **`crc=0` (deliberate)** — our frames carry their own CRC | see note |

> **Trap — do not misread our packet params.** `0x02 0x49 0x0C 0x4C 0x00 <len>` decomposes as
> preamble `0x0C` (preamble=8 | syncLen 4/2), then `0x4C` = `syncTx=1 | syncMatch=1 | fixed=1 |
> **crc=0**`, then `0x00`, then payload length. CRC is **intentionally disabled at the FLRC layer**
> because we run our own frame CRC. This is a design choice, **not** a bug, and it means any
> CRC-error statistic we collect is **our frame CRC**, not the chip's. (That is also why our
> 200/200-CRC-error result is a real frame-integrity failure rather than a chip CRC artefact.)

`NOT REACHED`: a field-by-field decode of ELRS's `SetFlrcModulationParams` argument construction
(the dead run was mid-extraction of datasheet §18.4.1 / §18.4.2 when it died). The bitrate enum and
the `0x25` CR/BT byte should be compared against ELRS's `FLRC_BITRATE_*` / CR constants as a
follow-up — it is a small, bounded task.

## Q4 — PA ramp / power table

**Partial.** We write `0x02 0x03 <pwr*2> 0x04` (verified at `esp_idf_lr2021_radio.cpp:339`), where
`0x04` is the ramp selector. Datasheet Table 7-21 (verified, `ds.txt:18841-18860`):
`0x00=2 µs, 0x01=4, 0x02=8, 0x03=16, 0x04=32, 0x05=48, 0x06=64, 0x07=80, 0x08=96, 0x09=112, 0x0A=128 …`.
So our `0x04` = **32 µs** — mid-table, not the slowest. Faster ramps down to **2 µs** exist. For a
burst protocol at high bitrate, ramp-up time eats into the preamble/guard budget.
`NOT REACHED`: ELRS's chosen ramp value. **REVIEW: consider a faster ramp.**

## Q6 — Our open short-payload CRC item, cross-checked

- Our own prior root cause (already established, **not** re-opened here): the 255-byte failures were
  a **wrong FIFO-clear opcode** — `{0x01,0x1E}` (no-op) vs the correct `{0x01,0x20}`; RX FIFO is
  ~256 B so one uncleared packet fills it. Source: `docs/255-BYTE-PACKET-INVESTIGATION.md`. **255 B is
  closed.**
- **Still unexplained:** 64 B / 128 B at 260/650 kbps → 200/200 CRC errors while 255 B is clean.
- **New lead from this audit:** the missing **PRAM patch** (Q5). An unpatched PHY is a plausible
  cause for a payload-length-dependent FLRC defect.
- `NOT REACHED`: whether ELRS's driver or commit history documents this exact failure. The dead run
  was querying ELRS's FLRC references when it died. Worth one grep over the ELRS repo + issues.

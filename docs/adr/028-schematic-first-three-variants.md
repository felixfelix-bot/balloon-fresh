# ADR 028: Schematic-First PCB Design with Three MCU Variants

## Status

Proposed

## Date

2026-08-05

## Related

- ADR-001: ESP32-C3 as MCU
- ADR-015: Three-Board Hardware Strategy
- ADR-026: Dual MCU Radio Architecture (RP2040 + C3)
- docs/coordination/CONSULTANT-STRATEGIC-REVIEW.md (root cause analysis)
- tracker/firmware/main/app_main.cpp (GPIO assignments)

## Context

### The Problem

The balloon project accumulated 33 PCB board file variants for a 17-component
board. Zero schematics existed. All boards were generated by Python scripts
(`gen_pcb.py`) with hand-coded netlists. No ERC (Electrical Rules Check) was
ever run. This caused:

1. **527 DRC violations** on the original board (shorts between SPI lines,
   power nets incompletely routed, board outline self-intersecting)
2. **MCU mismatch**: firmware targets ESP32-S3 (`sdkconfig`), board has
   ESP32-C3 footprint. The firmware cannot run on the board.
3. **7 consecutive kimi-k3 worker timeouts** (300s each) attempting to
   auto-route power nets (3V3, GND, VCAP) on a 2-layer board where component
   placement didn't cluster power islands
4. **No schematic = no ERC** = netlist errors propagate undetected into PCB
   layout, manifesting as shorts and unconnected pads

### Verified Facts

- Firmware: ESP-IDF, targets `CONFIG_IDF_TARGET="esp32s3"`, builds clean
  (22,465 LOC, 119 tollgate tests passing, FreeRTOS relay tasks implemented)
- Board: ESP32-C3 Mini-1 footprint in all 33 variants
- No `.kicad_sch` files exist anywhere in the repo
- Component placement was script-generated, not optimized for routing
- 2-layer power routing proven infeasible: straight tracks create shorts,
   L-routing needs spatial reasoning that exceeds 300s worker budget
- 4-layer (GND + 3V3 internal planes) eliminates all power routing

### Consultant Verdict

> "33 board variants + ~20 routing scripts for a 17-component board = profound
> process failure. A board this simple is hand-routed in one evening."

## Decision

### 1. Schematic-First Workflow (MANDATORY)

No PCB layout may be created without a corresponding schematic file
(`.kicad_sch`) that passes ERC. The workflow is:

```
Schematic (.kicad_sch) → ERC passes → PCB layout (.kicad_pcb) → DRC passes → Gerbers
```

The previous workflow (Python script → .kicad_pcb → DRC → re-script) is
**banned**. It produced 33 variants and zero working boards.

### 2. Three Board Variants

| Variant | MCU | Purpose | Priority |
|---------|-----|---------|----------|
| C3-Flight | ESP32-C3 Super Mini | Current testing, first flights | P0 (now) |
| S3-Future | ESP32-S3-WROOM-1 | Future custom board, migration target | P1 |
| C3+RP2040 | ESP32-C3 + RP2040-Zero | Dual-MCU: radio coprocessor + app | P2 |

All three share the same peripherals:
- NiceRF LoRa2021 (SPI)
- MAX-M10S GPS (UART)
- TPS7A02 regulator
- Supercapacitor + solar power architecture
- Status LED, voltage divider for VCAP monitoring

### 3. C3 is Current, S3 is Future

Felix is currently testing with ESP32-C3 Super Mini boards because they're
small, light, and inexpensive. The firmware will be ported to C3 for flight
testing. S3 migration happens when we have a proven custom board design.

### 4. Only kimi-k3 Does Spatial Work

All schematic drawing and PCB layout must be done by the `worker-layout`
profile (kimi-k3:cloud model). glm-5.2 and other models are **banned** from
schematic/PCB work. This is enforced by:
- worker-layout profile SOUL.md
- Memory entry
- Manager (this profile) never touches .kicad_sch or .kicad_pcb files

### 5. 4-Layer for Production Boards

The C3-Flight variant may use 2-layer (it's a carrier board for the C3 Super
Mini dev board, which is already a module). The S3-Future and C3+RP2040
variants use 4-layer (GND plane + 3V3 plane) to eliminate power routing.

## Invariants

1. Every `.kicad_pcb` file must have a corresponding `.kicad_sch` that passes ERC
2. Board thickness must be 0.6mm (pico balloon weight constraint)
3. GPIO9 = STATUS_LED on all C3 variants
4. No GPIO18/GPIO19 on C3 (they're USB pins, not broken out on Mini-1 module)
5. No FEM on flight boards (wire dipole only for V1 flights)
6. Only kimi-k3 (worker-layout) touches schematic and PCB files
7. Board outline must be present before gerber export

## Consequences

### Positive

- Schematic catches netlist errors before they reach PCB (ERC vs DRC)
- Three documented variants with clear migration path
- kimi-k3 spatial reasoning eliminates the routing automation rabbit hole
- 4-layer eliminates power routing entirely for production boards
- Breadboard validation possible immediately (no PCB needed for first tests)

### Costs

- Must port firmware from S3 to C3 for flight testing (different GPIO count,
  single core, less RAM)
- 4-layer boards cost ~$12-15 vs ~$2-5 for 2-layer at JLCPCB (~$10 difference)
- Must learn KiCad schematic workflow (was using script-generated boards)
- C3+RP2040 variant adds UART inter-MCU communication complexity

## Rollout

### Phase 1: Schematic Plans (NOW)
kimi-k3 writes complete netlists + GPIO tables for all 3 variants.
Output: `docs/coordination/SCHEMATIC-PLAN-3VARIANTS.md`

### Phase 2: Draw Schematics
kimi-k3 draws `.kicad_sch` files from the plan. Run ERC. Fix violations.

### Phase 3: PCB Layout from Schematics
kimi-k3 creates `.kicad_pcb` from schematic netlist. Hand-route or
Freerouting (SES import only). Run DRC. Export gerbers.

### Phase 4: Consultant Review
Consultant verifies each board: DRC clean, GPIO correct, thickness 0.6mm,
gerbers non-empty.

### Phase 5: JLCPCB Order
Felix orders boards. Breadboard validation in parallel (no PCB needed).

## Notes

This ADR supersedes the ad-hoc script-generated board workflow that produced
33 variants. ADR-015 (three-board strategy) and ADR-026 (dual-MCU) remain
valid — this ADR adds the schematic-first constraint and the C3/S3 split.

The 2-layer V2-ADC board (commit dd03b60) is kept as a backup with 16
unconnected power pads requiring manual KiCad GUI finish. It is not the
production path.

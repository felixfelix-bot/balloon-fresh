# P0.4 — ESP32-C3 SPI clock 40 MHz → 16 MHz (LR2021 datasheet compliance)

**Date:** 2026-09-11
**Task:** `t_0b2f5534` (P0.4)
**Parent audit:** `docs/lr2021-bottleneck-analysis-2026-07-29.md` § Bottleneck #2
**Plan:** `docs/lr2021-throughput-fix-plan-2026-07-29.md` § Task 0.4

## 1. What the change is

The ESP32-C3 bench HAL drove the LR2021 over GPSPI2 at **40 MHz** — 2.5× the
Semiconductor LR2021 datasheet maximum of **16 MHz** (`EspHalC3.h` line 31/32).
The clock is now capped at the datasheet maximum:

```c
// mesh-stack/flrc-bench-espidf/main/EspHalC3.h
#define ESPHAL_C3_SPI_HZ   (16 * 1000 * 1000)   // was (40 * 1000 * 1000)
...
dev_cfg.clock_speed_hz = ESPHAL_C3_SPI_HZ;      // single source of truth
```

The 16 MHz value is also what the firmware prints at boot
(`SPI+GDMA init: MOSI=.. MISO=.. SCK=.. 16MHz dma_tx=.. dma_rx=.. qs=8`), so a
flashed board self-reports the clock it actually configured.

## 2. Change provenance (already on `main`)

The change was authored during the 2026-07-29 speed campaign and is present in the
tree at `HEAD` as part of:

| Commit | Date | Content |
|--------|------|---------|
| `d7ba37a` | 2026-07-28 | introduced the GDMA HAL with `ESPHAL_C3_SPI_HZ (40 * 1000 * 1000)` |
| `02108f5` | 2026-07-29 | non-GDMA branch: `dev_cfg.clock_speed_hz` 18 MHz → 16 MHz + CHANGELOG |

Both `origin/main` and `origin/master` contain `8fd3d4e`, so the datasheet-compliant
clock is already published. This run added the regression gate, the impact model and
the build/artifact verification that the earlier attempts did not leave behind.

## 3. Verification performed (hardware-free)

### 3.1 Regression test — TDD RED → GREEN

New host-only test: `tests/test_c3_spi_clock.py` (8 tests, no board required).

```
# RED — run against the pre-fix GDMA HAL:
git show d7ba37a:mesh-stack/flrc-bench-espidf/main/EspHalC3.h > /tmp/EspHalC3_40MHz.h
C3_HAL_PATH=/tmp/EspHalC3_40MHz.h python3 -m pytest tests/test_c3_spi_clock.py -q
  -> FAILED test_spi_hz_macro_within_datasheet_max
     AssertionError: ESPHAL_C3_SPI_HZ = 40000000 Hz exceeds the LR2021 datasheet
     maximum of 16000000 Hz

# GREEN — current HEAD:
python3 -m pytest tests/test_c3_spi_clock.py -v
  -> 8 passed in 0.43s
```

The suite parses the HAL sources and asserts: the macro evaluates ≤ 16 MHz,
`dev_cfg.clock_speed_hz` is driven by the macro (no magic literals), no radio
source hard-codes a clock above spec, and both raw bench apps report the same
macro they configure. It also asserts the historical 40 MHz and 18 MHz values
would be rejected, so this cannot silently regress.

### 3.3 Compiled artifact proves 16 MHz

The ELF call-site constant handed to `spi_bus_add_device()` is 16 000 000, and
neither old clock value survives anywhere in the debug info:

```
readelf --debug-dump=info build_p04_raw_tx/flrc-bench-espidf.elf | grep 16000000
  <b26d5> DW_AT_GNU_call_site_value: 5 byte block: c 0 24 f4 0 (DW_OP_const4u: 16000000)

readelf --debug-dump=info ...elf | grep -E "40000000|18000000"
  (no matches)
```

Both RAW_TX and RAW_RX ELFs contain exactly one 16 000 000 constant and zero
occurrences of 40 MHz / 18 MHz.

## 4. Throughput impact model (answers ">20% drop → investigate")

No LR2021/C3 bench boards were connected to this machine during this run
(`lsusb`: only a Pico debugprobe, two CH340 adapters and the host's LTE modem —
no `303a` Espressif device, no RP2040 in app mode), so the on-air 1000-packet
test could not be executed. The impact was therefore modelled from the actual
per-packet SPI byte budget in `esp32_raw_tx.cpp`, anchored to the last measured
40 MHz result (`docs/CHANGELOG.md`, v0.2.0-p0.2: 1781.7 kbps, 255-byte payload,
SPI 40 MHz).

Per-packet SPI traffic on the RAW_TX happy path (payload = `FLRC_PKT_SIZE` = 255 B):

| Transaction | Bytes |
|-------------|-------|
| `rfClearIrq()` (0x0116 + 4-byte mask) | 6 |
| `rfWriteTxFifo()` (0x0002 + 255 B payload) | 257 |
| `rfSetTx()` (0x020D + 3 B) | 5 |
| `rfReadIrqStatus()` (2 + 6 B) × ~8 polls while waiting for TX_DONE | 64 |
| **total** | **332 B = 2656 bits** |

| Quantity | Value |
|----------|-------|
| RF air time (255 B @ 2600 kbps FLRC) | 784.6 µs |
| Measured packet period @ 40 MHz (1781.7 kbps) | 1145.0 µs |
| SPI bus time/packet @ 40 MHz | 66.4 µs |
| SPI bus time/packet @ 16 MHz | 166.0 µs (+99.6 µs) |
| **Predicted packet period @ 16 MHz** | **1244.6 µs** |
| **Predicted throughput @ 16 MHz** | **1639 kbps (−8.0%)** |
| 20% investigation budget | +229.0 µs/pkt (model uses 99.6 µs = 43% of budget) |

Conclusion: the change is **RF-bound, not SPI-bound** — air time is already 69%
of the 40 MHz packet period, and the extra 100 µs of bus time per packet costs
about 8% of throughput, comfortably inside the 20% investigation threshold. This
matches the plan's expectation ("no throughput gain; reliability improvement;
SPI is not the dominant time component on ESP32").

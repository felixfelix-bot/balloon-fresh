# P4.1 — DMA Chaining for Zero-Copy Packet Transfer (RP2040 + LR2021)

**Task:** t_4b8103d4 (child of P4.0 PIO-SPI `t_22d41c82` and the LR2021 test-plan CTX `t_95012e30`)
**Date:** 2026-08-01
**Platform:** RP2040 coprocessor + NiceRF LoRa2021 (Semtech LR2021 Gen 4), FLRC 2.4 GHz
**Reference firmware:** `firmware/rp2040/src/flrc_dma_chain_tx.cpp`
**Baseline (P3 blocking-DMA TX):** 1745 kbps, SPI 10.40 MHz, 0% loss (see `docs/RP2040-LR2021-BASELINE-v1.0.0.md`)

---

## 1. Problem statement

The Phase-3 DMA TX (`flrc_dma_tx.cpp`) uses **one DMA channel that is reconfigured from
scratch and fully synchronously waited on for every SPI transaction**. Per packet the CPU
executes six such transactions:

```
CLEAR_ERRORS → CLEAR_IRQ → CLEAR_TX_FIFO → WRITE_TX_FIFO(257 B) → SET_TX → spin-wait TX_DONE
```

Each call to `dmaSpiWrite()` does:
1. `dma_channel_get_default_config()` + four `channel_config_set_*()` — **full rebuild**
2. `dma_channel_configure()` + `dma_channel_start()`
3. `dma_channel_wait_for_finish_blocking()` — **CPU stalls until the last byte is clocked**
4. FIFO-drain spin loop

Plus the payload is **copied** every packet:
`memcpy(&dma_fifo_buf[2], pkt, FLRC_PKT_SIZE)` (255 B memcpy in the hot path).

Net effect: the DMA engine is not actually offloading the CPU — the CPU is awake for
every SPI cycle and pays a per-packet 255 B memcpy. The only phase the CPU is *not*
driving SPI is the ~785 µs on-air TX_DONE wait, which is where the cycle budget should be
spent re-arming the next packet instead.

## 2. The hard constraint — why a free-running packet DMA chain is impossible here

A natural reading of "DMA chaining for zero-copy transfer" is: *build N packet buffers,
chain N DMA control blocks, fire once, the DMA streams all N packets to the radio with no
CPU intervention.* **This is physically impossible on the LR2021, and the reason is the
radio, not the RP2040:**

| Fact | Consequence |
|------|-------------|
| The LR2021 holds **one** TX packet in its FIFO at a time. | You cannot preload N packets. |
| Each packet is radiated on air for `255×8 / 2.6 Mbps ≈ 785 µs`. | Throughput is air-limited, not SPI-limited. |
| Between commands the chip asserts **BUSY**; the master must wait for BUSY-low before the next CS-low. | The RP2040 DMA controller cannot observe BUSY — its triggers are DREQ / timer / chain only, **never a GPIO level**. GPIO can only raise an IRQ. |

So the entity that observes BUSY and steps the radio state machine **must** be the CPU (or
a PIO state machine wired for it). The DMA chain therefore cannot autonomously walk
packet→packet. Any design that claims otherwise would overrun the radio FIFO and corrupt
the link.

This is the single most important architectural fact for P4.1, and it reframes the task:
the deliverable is **zero-copy data movement + eliminated setup overhead**, not autonomous
packet streaming.

## 3. What P4.1 actually delivers

Four concrete mechanisms, all implemented in `flrc_dma_chain_tx.cpp`:

### 3.1 Zero-copy TX ring (headline)

A ring of `TX_RING_DEPTH` slots in SRAM. Each slot is laid out **exactly as the radio
expects on the wire**, with the WRITE_TX_FIFO header pre-baked:

```
slot[k] = [ 0x00 ][ 0x02 ][ payload[0..254] ]   (257 bytes, padded to 260, 4-byte aligned)
            └─ WRITE_TX_FIFO opcode ─┘
```

- The header bytes (`0x00, 0x02`) are written **once** at init and never touched again.
- The payload region is filled **in place** by the producer (the TX loop writes the 4-byte
  sequence counter directly into `slot[k][2..5]`). **No memcpy.**
- The DMA channel reads the slot directly — the same bytes the producer wrote are the bytes
  that hit MOSI. Zero intermediate copies.

This removes the 255 B per-packet memcpy of the P3 path entirely.

### 3.2 Pre-configured, reused DMA channel (the "chain" win in practice)

Instead of rebuilding the channel config every transfer (`dma_channel_configure`), the
FIFO-write channel is configured **once** at init (DREQ = SPI0 TX, read-increment,
write-fixed, size 8). The per-packet hot path becomes two register writes:

```c
dma_channel_set_read_addr(chFifo, slot[k], false);   // point at the ring slot
dma_channel_set_trans_count(chFifo, SLOT_LEN, false); // 257 bytes
dma_channel_start(chFifo);                            // go
```

`set_read_addr` / `set_trans_count` are single MMIO writes — orders of magnitude cheaper
than a full `channel_config` rebuild. The channel is **re-armed, not reconfigured**.

### 3.3 Pre-arm double-buffering (hide SPI setup behind air time)

While packet *k* is on air (the long TX_DONE spin), the producer:

1. Fills `slot[k+1]` with the next payload (in place, zero-copy),
2. Waits for the radio to return to STDBY (BUSY-low = TX_DONE),
3. Issues CLEAR_IRQ + CLEAR_TX_FIFO + SET_TX for packet *k+1*,

and the WRITE_TX_FIFO DMA for slot[k+1] is armed so it fires the instant the FIFO is clear.
The ~98 µs SPI cost of the 257-byte FIFO write (at 20.83 MHz via PIO, or ~196 µs at the
10.40 MHz HW-SPI baseline) is **hidden behind the 785 µs air time** of the previous packet.

### 3.4 `chain_to` self-reload burst primitive (the genuine DMA-chaining machinery)

For completeness and as the reusable primitive, `flrc_dma_chain_tx.cpp` also implements a
**true RP2040 chained-DMA ring** using the `chain_to` + reload-control-block pattern
(datasheet §2.5.6): channel `chData` does the byte transfer to SPI0 DR; on completion it
chains to `chReload`, whose single-word transfer writes `chData`'s next read-addr from a
control-block ring, restarting `chData` at the next slot.

This primitive **does** free-run — which is exactly why it is exposed only as a
`dma_chain_burst_fill()` helper for *within-transaction* bursts (e.g. streaming a long
header+payload as multiple chained fragments), and is **deliberately not** used to walk
whole packets (that would overrun the radio, §2). The design doc calls this out so a future
maintainer does not "improve" the loop into a free-running chain and silently corrupt the
link.

## 4. Expected impact

| Metric | P3 blocking DMA | P4.1 zero-copy chain | Source of gain |
|--------|-----------------|----------------------|----------------|
| Per-packet memcpy | 255 B | **0 B** | §3.1 ring |
| Per-FIFO-write DMA setup | full `channel_configure` | 2 MMIO writes | §3.2 reuse |
| FIFO-write SPI cost | visible (~196 µs @ 10.4 MHz) | hidden behind air time | §3.3 pre-arm |
| Air-time utilization | ~67% | → approaches 100% | smaller inter-packet gap |

Throughput is still **air-limited** (PHY max ≈ 2600 kbps); the win is closing the gap
between 1745 kbps and the air ceiling by removing dead time between packets, and freeing
the CPU to service RX / telemetry / mesh-stack work concurrently. CPU cycle budget freed
per packet: the ~196 µs FIFO write + the 255 B memcpy setup (~3 µs) ≈ **~0.2 ms/packet
returned to the application**.

## 5. Pin map & build

Pins mirror the rest of the RP2040 firmware (ADR-015):
`SCK=GP2  MOSI=GP3  MISO=GP4  CS=GP5  BUSY=GP6  IRQ=GP7  RST=GP8  LED=GP25`

Build (pico-sdk, framework-agnostic — no Arduino core dependency):

```bash
cd firmware/rp2040
mkdir -p build && cd build
cmake -DPICO_SDK_PATH=~/pico-sdk ..
make -j$(nproc) dma_chain_tx        # -> dma_chain_tx.uf2
```

> **Toolchain note:** the system `arm-none-eabi-gcc` (14.2.1) is missing newlib
> (`nosys.specs` / `libc.a`), which breaks the pico-sdk `boot_stage2` sub-build
> with `cannot read spec file 'nosys.specs'`. Two fixes:
> 1. `apt install libnewlib-arm-none-eabi` (system gcc, 14.2), **or**
> 2. point CMake at PlatformIO's bundled toolchain (9.2.1, complete newlib) and
>    put its `bin/` first on PATH:
>    ```
>    export PATH=~/.platformio/packages/toolchain-gccarmnoneeabi/bin:$PATH
>    PIO=~/.platformio/packages/toolchain-gccarmnoneeabi/bin
>    cmake -DPICO_SDK_PATH=~/pico-sdk \
>          -DCMAKE_C_COMPILER=$PIO/arm-none-eabi-gcc \
>          -DCMAKE_CXX_COMPILER=$PIO/arm-none-eabi-g++ ..
>    ```
> Option 2 was used to verify this build (zero warnings, 80 KB UF2).

A new `add_executable(dma_chain_tx ...)` target is added to `CMakeLists.txt`; it does **not**
require pioasm (no `.pio`), so it builds even where the PIO assembler is unavailable.

## 6. Hardware test plan (run when a dedicated radio link is available)

> The RP2040 TX board is one half of a link — a verified **RX** board (ESP32 or 2nd RP2040
> running a known-good RX firmware, e.g. `flrc_raw_rx.cpp`) is required to measure PER.
> Flashing follows the board-mutex / FLASH-QUEUE protocol in the project `AGENTS.md`.

| Step | Action | Pass criterion |
|------|--------|----------------|
| 1 | Build `dma_chain_tx.uf2`, flash to RP2040 (BOOTSEL → copy UF2 to RPI-RP2). | Board enumerates, `INIT` reports `RADIO_INIT_OK`. |
| 2 | Stand up RX board with `flrc_raw_rx` at 2440 MHz, FLRC, sync `12 AD 10 1B`. | RX prints `RX_READY`. |
| 3 | Send `RUN` over USB CDC (or Serial1 UART GP12). TX emits 1000 pkts. | `TX_DONE_STATS: fired=1000 timeout=0`. |
| 4 | Read RX counters. | **RX ≥ 990/1000 (≤1% PER)** at 1 m, matching the 0%-loss baseline. |
| 5 | Read `RESULT_TX throughput_kbps`. | **≥ baseline 1745 kbps**, target ≥ 1900 kbps. |
| 6 | Logic-analyzer capture of CS/SCK/MOSI/BUSY across 3 packets. | Inter-packet BUSY-low gap shrunk vs P3; no FIFO overrun (no CMD_ERROR IRQ). |
| 7 | Stress: `TX_PKT_COUNT=10000`, log any `CMD_ERROR` / timeout accumulation. | 0 CMD_ERROR; <0.1% timeout. |

## 7. Relationship to PIO (P4.0)

This reference build uses the RP2040 **hardware SPI peripheral** (DREQ `spi_get_dreq(spi0,
true)`) so the DMA-chaining mechanism is isolated and the file compiles standalone without
pioasm. To obtain the 20.83 MHz SPI clock of P4.0's PIO engine, swap **one line**: point
the DREQ at the PIO state machine (`pio_get_dreq(pio, sm, true)`) and the write target at
`&pio->txf[sm]`. The zero-copy ring, the reused channel, and the pre-arm timing are
identical — the SPI clock source is orthogonal to the DMA-chaining design.

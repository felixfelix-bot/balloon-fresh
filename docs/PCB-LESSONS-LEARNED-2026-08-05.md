# PCB Pipeline Lessons Learned (2026-08-05)

## Context

Attempted to build ESP32-C3 balloon relay PCBs programmatically (Python + pcbnew API).
Generated 33 board variants across 2 sessions. None fabrication-ready. Root causes documented below.

---

## 1. MODEL SELECTION: Wrong model for wrong task

**What happened:** Assigned kimi-k3:cloud for all PCB work because "Kimi = spatial reasoning."

**Root cause:** Research shows kimi-k3 excels at VISUAL spatial reasoning (looking at images).
PCB generation via Python pcbnew API is PROGRAMMATIC — it requires mathematical coordinate
calculation, constraint satisfaction, and rule adherence. GLM 5.2 is stronger at exactly this.

**Lesson:** Match the model to the actual cognitive task, not the domain label.
- Programmatic PCB generation (scripts, coordinates, constraints) → GLM 5.2
- Visual PCB inspection (rendered images, layout review) → Kimi K2.7 (local, multimodal)
- kimi-k3:cloud is expensive AND was quota-exhausted → use two-stage pipeline instead

**Action:** Two-stage pipeline documented in PCB-TWO-STAGE-PLAN.md.

---

## 2. SILENT MODEL FAILURE: Empty boards committed

**What happened:** worker-layout was configured for kimi-k3:cloud. The model was quota-exhausted
and silently failing. The proxy returned empty responses. Workers committed empty .kicad_pcb files
(0 footprints, 0 tracks) thinking they had succeeded.

**Root cause:** No quality gate caught empty output. DRC reported "0 violations / 0 unconnected"
which looked perfect — because there was nothing on the board to violate.

**Lesson:** "0 violations" on an empty board is not success. Always verify content exists before
treating DRC as passed.

**Action:** Quality gate added: F_Cu gerber must have >10 aperture draws (non-empty check).
Pre-commit assertion: `assert len(b.Footprints()) >= 17`.

---

## 3. NO SCHEMATIC: 33 board variants without ERC

**What happened:** All 33 board variants were generated by Python scripts (full_pipeline.py).
No .kicad_sch files existed. No Electrical Rules Check (ERC) was ever run. Components were placed
by guessing coordinates, not by deriving from a verified netlist.

**Root cause:** Started with board layout (bottom-up) instead of schematic design (top-down).
The industry-standard flow is: Schematic → ERC → Board → DRC → Gerbers.

**Lesson:** Schematic-first is mandatory. A schematic with ERC catches pin conflicts, floating
nets, and power issues BEFORE board layout begins. Without it, every board variant is a guess.

**Action:** ADR-028 mandates schematic-first for all 3 variants. ERC must pass before board layout.

---

## 4. 2-LAYER ROUTING CONVERGENCE: Power nets dominate

**What happened:** On a 2-layer board with 17 components, 50% of unconnected nets were power
(GND and 3V3). FreeRouting auto-routed 85% of signals but the remaining 15% (scattered power
pads) couldn't be routed without cutting through signal traces — creating 36+ shorts.

**Root cause:** On 2-layer boards, power and signal share the same copper layers. GND needs to
reach scattered pads across the board, consuming routing channels that signals need.

**Lesson:** 4-layer boards with internal GND and 3V3 planes eliminate this entirely.
Power pads auto-connect through vias to internal planes. Outer layers are dedicated to signals.

**Cost difference:** $2 (2-layer) vs $8 (4-layer) for 5 boards at JLCPCB. $6 difference — negligible.

**Action:** 4-layer is the default for all variants (ADR-028).

---

## 5. PIN CONFLICTS: Board design didn't match firmware

**What happened:** The PCB execution plan specified GPIO9 for STATUS_LED, but firmware uses GPIO18.
The plan mapped FEM_TX to GPIO19 (USB pin) without noting the conflict. Board thickness was
listed as both 0.6mm and 1.6mm in different sections.

**Root cause:** Plan was written without reading the firmware source. Assumptions were made
about pin assignments instead of verifying from app_main.cpp.

**Lesson:** Always verify pin assignments from firmware source code, not from documentation.
Firmware is the source of truth for what GPIO the hardware must expose.

**Action:** Verified C3 pin map extracted from app_main.cpp:85-94 and embedded in all task specs.
FEM_RX moved from GPIO0 (strapping pin) to GPIO8.

---

## 6. TIMEOUTS: delegate_task 300s too short for complex work

**What happened:** kimi-k3:cloud tasks timed out 8 times. Each timeout wasted 5 minutes of API
calls for partial work that was discarded.

**Root cause:** Global delegate_task child_timeout_seconds was 0 (defaulting to hardcoded 300s).
Complex multi-file tasks need 500-800s minimum.

**Action:** child_timeout_seconds set to 1800s (30 min) in ~/.hermes/config.yaml.
max_async_children increased from 3 to 6.

---

## 7. WORKER PROFILE MODEL ASSIGNMENT

**What happened:** worker-layout was configured for kimi-k3:cloud. When quota exhausted, all
tasks routed to this profile silently failed or fell back to weaker models.

**Lesson:** Worker profile model assignments must be verified against actual availability before
dispatching tasks. Always test the model endpoint before creating a task pipeline.

**Action:** Model availability check is now standard pre-dispatch: test endpoint with tiny request
before creating kanban tasks.

## 8. PLACEMENT BEFORE ROUTING (breakthrough)

**What happened:** Previous attempts routed immediately after placing components, producing 13 shorting items from overlapping footprints that no amount of DRC iteration could fix — the components were physically colliding.

**Root cause:** Placement and routing were treated as a single combined step. No verification gate existed between "components placed" and "tracks routed." Overlapping footprints propagated shorts into the routing; the router then dutifully connected them — creating copper bridges between components that should never have touched.

**Fix:** Gate 0 placement check inserted BEFORE any routing (see §4.0 of PCB-TWO-STAGE-PLAN.md). Rules enforced:
- 0.5mm margin on every component bounding box
- 2mm minimum gap between bounding boxes
- Placement must pass before any track creation

**Result:** Phase 1 placement PASSED with `shorting_items: 0`, `solder_mask_bridge: 0`. Board expanded to 55×45mm to give components adequate room.

**Lesson:** Placement and routing are SEPARATE phases. Never route on unverified placement. A placement gate catches footprint collisions before they become intractable routing failures.

---

## 9. BOARD SIZE MATTERS

**What happened:** Attempted to fit 17 components on 35×30mm and 45×35mm boards. Both too small — components could not be placed without bounding-box overlap.

**Root cause:** Over-constrained board size driven by pico-balloon weight optimization. For 17 components including QFN32 (ESP32-C3-MINI-1), LR2021 module, GPS (MAX-M10S), and assorted passives, 35×30mm and 45×35mm simply do not provide enough area for 2mm-gap placement.

**Fix:** Board expanded to 55×45mm. Adequate spacing for QFN32 + LR2021 module + GPS + passives, all with 2mm minimum gaps.

**Lesson:** Don't over-constrain board size. For a pico balloon, weight savings from a smaller PCB are marginal vs the risk of routing failure (13+ shorts, weeks of DRC iteration). The PCB is ~3g; the difference between 45×35mm and 55×45mm is well under 1g. Not worth the routing pain.

---

## 10. PHASED EXECUTION WORKS

**What happened:** Single-pass "generate the whole board" tasks repeatedly failed at different stages with no clean recovery point. A mistake in placement wasn't discovered until routing failed, by which point everything had to be redone.

**Fix:** Task broken into three gated phases:
- **Phase 1 (Placement):** components placed, Gate 0 passed
- **Phase 2 (Routing):** tracks/vias created on F.Cu/B.Cu with GND+3V3 internal planes
- **Phase 3 (Verify):** DRC + gerber export + visual check

Each phase has its own quality gate. The worker can be told "stop after placement, verify, then continue" — giving clean checkpoints where errors are caught and fixed in isolation.

**Lesson:** Complex tasks succeed when broken into gated phases with verification between them. A single "make the board" prompt gives the model no place to recover from an early-stage mistake. A phased prompt lets placement errors get fixed before they poison routing.

---

## 11. KIMI K2.7 (LOCAL) IS SUFFICIENT FOR PCB WORK

**What happened:** kimi-k3:cloud quota was exhausted and the model was unavailable. PCB work appeared blocked — the original plan (ADR-028, PCB-EXECUTION-PLAN.md) had hardcoded kimi-k3:cloud as the ONLY model for all schematic and board layout work.

**Root cause:** Single-model dependency on a quota-limited cloud API. When quota ran out, the entire pipeline stalled with no fallback.

**Fix:** kimi-k2.7-code (local ollama, free, unlimited) was assigned the placement task. It successfully placed all 17 components with 0 bounding-box overlaps on a 55×45mm board.

**Lesson:** Local models can handle PCB generation when given proper structure (phases, gates, pre-layout math). The bottleneck was never the model — it was the lack of structure. With phased execution and explicit Gate 0 placement checks, kimi-k2.7-code matches or exceeds what kimi-k3:cloud produced unstructured. No cloud credit needed for spatial reasoning work.
